# Interview Stories — Six Guardrails (Single Author)

**Group 7 · Audrey Rah**

All six narratives below were written by the same developer who implemented the corresponding guardrails and integrated them into `main_system.py`. Folder names `student_1_loop` … `student_6_tokens` are assignment-required labels for failure-mode packages.

## 1. Infinite Graph Loops (`student_1_loop`)

During integration testing of the academic research orchestrator, I observed the coordinator re-dispatching rejected validation cycles without a hard stop. In an unguarded simulation the retry loop burned 100 iterations and about 12,000 approximate tokens before a safety hard-cap halted the run. After I implemented deterministic `round_number` tracking against the frozen shared contract, any retry storm that reaches `round_number >= 5` routes to a graceful partial-output node instead of continuing indefinitely. With the guardrail enabled, the same perpetual-rejection scenario terminates in six coordinator steps at round five, cutting token spend to about 720 units and collapsing measured latency relative to the unguarded path, while preserving a usable partial result for operators. The quantitative before/after comparison—including 11,280 tokens saved—is recorded in `student_1_loop/metrics.md` and reproduced by `test_failure.py`, giving a concrete production control for runaway graph recursion without relying on prompt instructions alone. That code-enforced ceiling is what I would cite in a production multi-agent reliability interview.

## 2. Silent Hallucination / Structural Failure (`student_2_silent`)

The analyzer worker occasionally returned plausible JSON that omitted mandatory domain fields such as methods or limitations coverage. Without schema enforcement those payloads looked successful in logs while poisoning downstream reviewers. Worker A uses an offline structured-output double that mirrors the `.with_structured_output(ContractSchema)` interface for deterministic testing; this offline simulation binds the frozen `AnalysisPayload` contract and is not a live LLM call. I then measured an elevated invalid-payload rate on synthetic malformed drafts along with a non-zero missing-field error count. Across five samples, eighty percent failed without retry and eight validation errors were counted. Enabling a single automated correction retry recovered all four repairable cases at one hundred percent correction success; a second failure still rejects the payload rather than silently continuing. `student_2_silent/test_failure.py` records invalid-payload rate, missing-field totals, and correction success rate. This code-level contract check closes the silent-hallucination gap that prompt wording alone cannot guarantee in a multi-agent pipeline and is the quantified reliability story I take into technical interviews.

## 3. Rogue Tool Execution (`student_3_rogue`)

While exercising the independent reviewer worker, I injected unauthorized tool names such as database deletion and trade execution, plus malformed allowlisted calls missing required arguments. With the middleware disabled, those names reached the tool runtime; dangerous implementations remain mocked so no real side effects occur, but the attempt path is still counted as an unsafe execution attempt. With the hardcoded allowlist and argument matrix I enabled, unauthorized tools raise `InvalidToolCallException` before dispatch, and incomplete argument sets are rejected as malformed. Metrics show two blocked unauthorized calls, one malformed request rejected, two unsafe attempts on the unguarded path, and zero successful unsafe executions after the guardrail. This dynamic tool-call gate is the difference between a demo agent that can be socially engineered into harmful actions and a production worker with an enforceable capability boundary aligned to the shared contract, which is the quantified reliability claim I emphasize.

## 4. Downstream Cascade Failure (`student_4_cascade`)

Malformed upstream state—an empty analysis payload without `paper_id`—caused the reporter path to throw `KeyError` and abort the run. Across twenty deterministic trials the unguarded downstream path crashed every time. I inserted an explicit sanitization node between upstream actor output and reporting that checks structural invariants before execution, converting those crashes into rollback responses that set a rejection flag for coordinator-driven recovery. After the guardrail, downstream crashes dropped to zero of twenty and rollback success reached one hundred percent on the same malformed inputs, while valid payloads with `paper_id` rs-10485157 still proceed normally through reporting. Capturing crash counts and rollback rate in `student_4_cascade/metrics.md` made the failure mode interview-ready: validation is a hard gate that prevents one bad worker payload from cascading through the graph, and those before-and-after numbers are the evidence I present when discussing defensive multi-agent design with hiring managers.

## 5. Data Privacy Leak Through Telemetry (`student_5_trace`)

Trace events in the orchestrator originally echoed emails, API key material, local filesystem paths, and personal names. That is unacceptable for coursework demos and for any environment that may export spans to a tracing backend such as LangSmith. I added a centralized State Redaction Interceptor that programmatically scrubs secrets, emails, names, and path prefixes before events are written to telemetry storage. On a fixed set of four synthetic events, six sensitive values were detected before redaction; after interception, leaked values fell to zero, yielding one hundred percent measured redaction accuracy on that suite. The before/after table in `student_5_trace/metrics.md` is reproducible via `test_failure.py`, demonstrating that privacy controls belong in code at the telemetry boundary rather than in informal logging discipline alone. That six-to-zero leak reduction is the quantified privacy outcome I highlight in professional engineering conversations about production observability.

## 6. Context Window Explosion and Token Burn (`student_6_tokens`)

Running twenty isolated reviewers naively accumulates every prior review and tool dump into a shared message list, exploding approximate token counts and slowing context assembly. I simulated twenty full reviewer outputs plus tool payloads and measured about 12,574 approximate tokens across forty-one messages with higher concatenation latency. I then added a context-management node that counts tokens against a soft limit from the contract, summarizes older messages, prunes redundant tool output, and preserves critical structured identifiers from the frozen shared schema. After pruning, token counts dropped to 655—about a 94.8 percent reduction—with only four messages retained and lower context-assembly latency, while reviewer isolation still keeps each Worker B run free of peer reviews. Those measured reductions are checked into `student_6_tokens/metrics.md`, turning an abstract context-window risk into an operational budget control for long multi-agent jobs and a clear cost-efficiency story for interviews.
